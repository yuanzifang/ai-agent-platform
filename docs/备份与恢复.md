# 备份与恢复

本文覆盖平台三类持久化数据的备份、校验和恢复演练：

| 数据 | 内容 | 备份方式 |
|---|---|---|
| MySQL | 业务表、对话、审计、用量、权限 | `mysqldump --single-transaction` + gzip |
| PostgreSQL/pgvector | 知识库向量、按维度分表 | `pg_dump -Fc` |
| MinIO | 附件、知识库原文件 | `mc mirror --preserve` |

Redis 不作为持久化备份对象：限流计数、SSE live 快照都是可重建数据；Redis 重启后会话可重新加载，进行中的流会中断。Ollama 模型可重新拉取，也不在备份范围。

## 1. 快速使用

```bash
# 全量备份到 backups/backup-YYYYMMDD-HHMMSS/
./scripts/backup.sh

# 只备份 MySQL + PgVector
./scripts/backup.sh --skip-minio

# 恢复演练（默认读取 backups/latest，自动创建/删除临时库与临时 bucket）
./scripts/restore-drill.sh

# 指定备份目录
./scripts/restore-drill.sh --backup backups/backup-20261020-140643
```

依赖：`mysql`/`mysqldump`、`psql`/`pg_dump`/`pg_restore`、`mc`、`gzip`、`python3`。

`pg_dump`/`pg_restore` 主版本必须不低于 PostgreSQL 服务端主版本。例如本机 PostgreSQL 17 + 默认 pg_dump 16 会失败，需要：

```bash
PG_DUMP=/opt/homebrew/opt/postgresql@17/bin/pg_dump \
  ./scripts/backup.sh
```

脚本会自动使用 `pg_dump` 同目录下的 `pg_restore`。

## 2. 配置

脚本优先读取仓库根目录 `.env`，也支持环境变量覆盖：

| 变量 | 默认 | 说明 |
|---|---|---|
| `BACKUP_ROOT` | `<repo>/backups` | 备份根目录 |
| `MYSQL_HOST` / `MYSQL_PORT` | `127.0.0.1` / `3306` | MySQL 地址 |
| `MYSQL_DATABASE` | `ai_agent_platform` | 库名 |
| `MYSQL_BACKUP_USER` | `root` | 建议单独建只读备份账号 |
| `MYSQL_BACKUP_PASSWORD` | 根密码/app 密码 | 不建议写进命令行 |
| `PG_URL` 或 `PG_HOST/PG_PORT/PG_DATABASE` | `vector` | 支持 `jdbc:postgresql://host:5432/db` |
| `PG_USERNAME` / `PG_PASSWORD` | 当前系统用户 / 空 | 生产用独立只读账号 |
| `MINIO_ENDPOINT` | `http://127.0.0.1:9000` | S3 端点 |
| `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | `MINIO_ROOT_USER/PASSWORD` | 建议只读账号 |
| `MINIO_BUCKET` | `ai-agent-platform` | 附件/知识库文件 bucket |
| `BACKUP_RETENTION_DAYS` | `14` | 仅配合 `--prune` 生效 |
| `BACKUP_OFFSITE_ENDPOINT` | 空 | 异地 MinIO/S3 兼容端点；配置后启用上传 |
| `BACKUP_OFFSITE_BUCKET` | 空 | 异地备份 bucket（自动创建） |
| `BACKUP_OFFSITE_ACCESS_KEY` / `BACKUP_OFFSITE_SECRET_KEY` | 空 | 异地最小权限账号 |
| `BACKUP_OFFSITE_PREFIX` | `ai-agent-platform` | 异地对象前缀 |
| `BACKUP_ENCRYPT_KEY_FILE` | 空 | 异地备份加密密钥文件；启用异地时必填 |

安全要求：

- 备份目录包含用户数据，脚本默认 `umask 077`，目录/文件仅当前用户可读。
- 不要把 `.env`、JWT/AES 密钥打进备份；本脚本不会复制 `.env`。
- 备份介质应加密（磁盘加密、S3 SSE、restic 等），并复制到异地/对象存储；脚本只负责本地归档。
- 生产建议使用最小权限账号：MySQL `SELECT, LOCK TABLES, SHOW VIEW, TRIGGER, EVENT`；PG `CONNECT, USAGE, SELECT`；MinIO 只读 policy。

### 2.1 异地加密上传

2026-10-26 已验证：备份完成后打包为 `backup-*.tar.gz`，用 `openssl enc -aes-256-cbc -pbkdf2` 加密，上传到 MinIO，并下载回读做 SHA256 比对。

```bash
# 只生成一次，离线保存；丢失后异地备份不可恢复
openssl rand -hex 32 > /secure/backup.key
chmod 600 /secure/backup.key

BACKUP_OFFSITE_ENDPOINT=https://minio.example.com \
BACKUP_OFFSITE_BUCKET=platform-backups \
BACKUP_OFFSITE_ACCESS_KEY=backup-writer \
BACKUP_OFFSITE_SECRET_KEY='***' \
BACKUP_OFFSITE_PREFIX=prod \
BACKUP_ENCRYPT_KEY_FILE=/secure/backup.key \
./scripts/backup.sh --prune
```

- 本地仍保留未加密目录用于快速演练；异地只上传加密归档
- 上传后校验远端对象 SHA256；失败时脚本退出非 0（本地备份仍保留）
- 可用 `--skip-offsite` 临时只做本地备份
- 建议给异地 bucket 配版本化/对象锁/生命周期，脚本不替代这些策略

恢复异地归档：

```bash
mc alias set offsite https://minio.example.com <access> <secret>
mc cp offsite/platform-backups/prod/backup-YYYYMMDD-HHMMSS.tar.gz.enc /tmp/
openssl enc -d -aes-256-cbc -pbkdf2 -pass file:/secure/backup.key \
  -in /tmp/backup-YYYYMMDD-HHMMSS.tar.gz.enc | tar -xz -C /tmp/restore
./scripts/restore-drill.sh --backup /tmp/restore/backup-YYYYMMDD-HHMMSS
```

## 3. 备份产物

```text
backup-20261020-140643/
├── README.txt
├── SHA256SUMS
├── manifest.json
├── mysql/
│   ├── ai_agent_platform.sql.gz
│   ├── checksums.tsv
│   ├── binlog.txt          # 可用于 PITR 定位；权限不足时为空并记录 warning
│   └── tables.txt
├── pgvector/
│   ├── vector.dump
│   ├── counts.tsv
│   └── toc.txt
└── minio/
    └── ai-agent-platform/  # bucket 内容镜像
```

- `manifest.json`：时间、主机、git commit、三类数据表/对象数量、文件 SHA256、warnings。
- `SHA256SUMS`：覆盖所有 dump、清单文件和 `manifest.json`；恢复前强制校验，损坏备份不会进入恢复流程。该文件用于防损坏/误改，不是数字签名；防恶意篡改需配合对象锁/WORM/异地只读存储。
- `latest` 是最近一次成功备份的符号链接；失败时 `.partial` 目录会被删除，不会发布半成品。若进程被 `kill -9`，可能残留 `.backup.lock` 或 `.partial`，确认无备份进程后手动清理。

### 一致性说明

- MySQL 使用 `--single-transaction` 获取 InnoDB 一致性快照；备份期间仍可写入。
- `checksums.tsv` 是备份开始时的表校验和。若备份期间有写入，恢复后的表校验和可能与它不同；严格演练应停写/低峰执行，或使用 `--allow-drift` 只验证表结构、行数可恢复。
- PgVector 使用 `pg_dump` 的一致性快照；恢复时按 `counts.tsv` 比对每张表行数。
- MinIO 备份按对象当前版本镜像；**不包含历史版本/删除标记**。需要版本级恢复时开启 bucket versioning + 复制/对象锁。
- 脚本不备份 MySQL binlog 文件本身，只记录坐标；PITR 需要单独保留 binlog 归档。

## 4. 定时任务与保留

```cron
# 每天 02:30 备份，保留 14 天
30 2 * * * cd /opt/ai-agent-platform && \
  BACKUP_ROOT=/data/backups ./scripts/backup.sh --prune --retention-days 14 \
  >> /var/log/ai-agent-backup.log 2>&1

# 每周日 04:00 做恢复演练
0 4 * * 0 cd /opt/ai-agent-platform && \
  BACKUP_ROOT=/data/backups ./scripts/restore-drill.sh \
  >> /var/log/ai-agent-restore-drill.log 2>&1
```

建议把演练结果接入监控/通知；连续失败要告警。备份完成后应尽快复制到异地，单机同盘备份无法应对磁盘/主机故障。

## 5. 恢复演练做了什么

`restore-drill.sh` 不会碰生产库/生产 bucket，只使用：

- MySQL 临时库：`ai_agent_platform_drill_*`
- PgVector 临时库：`vector_drill_*`
- MinIO 临时 bucket：`restore-drill-*`

流程：

1. 按 `SHA256SUMS` 校验所有备份文件。
2. MySQL：建临时库 → 导入 dump → 比对全部业务表（V50 后 80 张）的 `CHECKSUM TABLE` 和审计行数。
3. PgVector：建临时库 → `pg_restore` → 比对所有用户表行数。
4. MinIO：建临时 bucket → 从备份镜像回去 → 再下载一份 → 逐对象 SHA256 对比。
5. 无论成功失败，删除临时库/临时 bucket/临时配置文件。

生产恢复步骤（人工维护窗口）：

```bash
# 1. 停止写入（停后端）
docker compose --env-file .env.docker stop backend

# 2. 先备份当前状态，避免恢复错版本后无法回退
./scripts/backup.sh

# 3. MySQL 恢复（示例；生产库名以实际为准）
gunzip -c backups/latest/mysql/ai_agent_platform.sql.gz | \
  mysql -h <host> -u <user> -p ai_agent_platform

# 4. PgVector 恢复（先确认扩展与版本）
pg_restore -h <host> -U <user> -d vector --clean --if-exists \
  --no-owner --no-privileges backups/latest/pgvector/vector.dump

# 5. MinIO 恢复
mc alias set prod https://minio.example.com <access> <secret>
mc mirror --overwrite backups/latest/minio/ai-agent-platform prod/ai-agent-platform

# 6. 启动后端，检查 Flyway/健康检查/审计链
docker compose --env-file .env.docker start backend
curl -fsS http://127.0.0.1:8080/actuator/health
# 登录后：GET /api/v1/audit/verify
```

恢复后必须做：

- `GET /actuator/health` 为 `UP`
- 登录/租户隔离、对话、知识库检索最小验证
- `/api/v1/audit/verify` 返回 `valid=true`（若备份时审计链有效）
- 检查 Flyway schema version 与备份版本一致；跨版本恢复时先按发布说明升级

## 6. 已验证与边界

2026-10-20 本机原生服务（非 Docker）实测：

- 备份：MySQL 80 表 / 112K dump，PgVector 2 表 / 12K dump；MySQL+PgVector 备份 168K。MinIO 单独测试 3 对象 / 4130 bytes。
- 恢复：80 张 MySQL 表 `CHECKSUM TABLE` 不一致 0，审计 226 条；PgVector 2 表行数一致；MinIO 3 对象回读 SHA256 一致。
- 负面验证：篡改 `SHA256SUMS` 后演练退出码 1，未进入数据库恢复。
- 演练后临时库、临时 bucket、备份目录均已清理；业务基线保持 3 Agent / 13 会话 / 0 用例 / 0 用量，审计链 226 条有效。

尚未验证/未覆盖：

- Compose 部署：MySQL/PgVector 未暴露宿主机端口，默认需在容器网络内或跳板机执行；尚未在 Compose 栈内实跑备份。
- **异地对象存储上传 + 归档加密已验证**（2026-10-26：本机 MinIO，加密上传/下载 SHA256/解密/恢复演练通过）。
- 仍缺：Helm/K8s CronJob、binlog 随备份归档与 PITR 自动恢复、异地对象版本化/对象锁/生命周期、RTO/RPO 实测。
- 大库备份性能未压测；生产建议只读副本/维护窗口。
