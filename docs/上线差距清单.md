## 七、MVP 判定标准

1. 一个未接触过项目的客户，从注册到发布 Agent 全程无开发者介入；
2. 性能、备份、安全均有实测数据；

三条全满足，才算 MVP 产品。

## 八·二、架构演进评估与边界守卫（2026-10-27）

**结论：保持模块化单体 + 独立小进程（agent-gateway/alert-relay/沙箱执行器）+ 托管中间件；不做网关独立与平台拆分，直至下表触发条件真实发生。**

| 提议 | 现状 | 决策 |
|---|---|---|
| 前后分离 | 已是（Vue SPA + REST/SSE） | 无需变动 |
| 中间件独立部署 | 已是（Compose/Helm 独立容器+健康检查，外接 MinIO 模式已验证） | 生产用**托管服务**（云 RDS/Redis/对象存储），优先级高于自建拆分 |
| 统一网关独立 | gateway 模块约 600 行、零业务模块依赖（ArchUnit 守卫）、路由/Key/限流数据在主库 | 不拆；外部调用者 QPS 持续高于平台内部负载或需独立扩缩/WAF 时摘出（模块已可干净搬走） |
| Agent 平台拆分 | 模块化单体 15+ 模块，跨模块本地事务（父子块同成同败、审计哈希链） | 不拆；拆分打破事务与全链路透传（X-Gray-Tag/TenantContext/Trace），1–2 人团队运维成本翻倍，且不推进 MVP 任何一条标准 |

**拆分触发条件（数据到了才动手，写入即防拍脑袋）：**
1. **技能脚本执行器**：脚本并发导致平台 P95 劣化 >20% → 独立为执行服务（容器沙箱已备，最可能先触发）；
2. **统一网关**：外部调用者 QPS 持续高于平台内部负载 / 需独立扩缩或 WAF；
3. **知识检索**：向量检索 QPS 或库规模需独立扩容/换专用向量引擎；
4. **团队**：>5 人需要独立发布节奏，按团队边界拆。

**边界守卫（本提交）**：`ArchitectureTest`（ArchUnit）钉住三条——① gateway 不被任何模块依赖；② gateway 保持薄层、不依赖业务模块；③ deploy 运行时仅允许 agent 生命周期依赖（摘出前需事件化解耦，注释已写明）。边界腐烂即 CI 红。

**替代优先级**：全栈 k6 压测拿容量基线（单机撑多少租户 = 何时拆的决策数据）> 托管中间件 > ArchUnit 守卫（已做）> 拆分。
