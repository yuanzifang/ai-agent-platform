# Qwen3.8 27B 模型长稳验收（2026-11-02）

## 平台级 30 分钟长稳（Linux 后端）

在 UTM Linux 后端 `http://192.168.64.2:18080` 上使用 k6 跑了 1 VU、30 分钟、无 RAG 的短回答平台链路（模型 `qwen3.8:27b`）：

| 指标 | 结果 |
|---|---:|
| 完成迭代 | 530 |
| chat_ok | 65.5% |
| HTTP 请求失败率 | 34.1% |
| TTFB p95 | 75.3ms |
| 整轮 avg / p95 | 2388.6ms / 13756.3ms |
| 请求数 | 537 |

这是**平台级失败**：30 分钟持续单并发下约三分之一请求未完成/超时。qwen3.8 直连模型本身可用，但在平台 SSE/会话/默认生成长度组合下不具备在线长稳能力。因此不能把本轮写成“平台长稳通过”。

> 说明：k6 使用了 `--no-thresholds` 仅为了收集完整指标；若套用默认在线阈值，同样会失败。测试 Agent 已清理。

## 结论

**模型可用性通过，在线延迟 SLO 不通过。**

`qwen3.8:27b` 可以在本机持续运行 30 分钟，单并发短回答请求 589/589 成功、0 失败；
但持续负载后延迟明显上涨（后 100 次平均 5.9s，p95 11.1s，最大 21.0s），
且 Ollama RSS 从约 15.4GB 涨到 34.2GB。因此：

- **可作为离线/交叉验证模型的长稳测试**
- **不应作为在线主模型的容量或延迟验收依据**
- 平台级 SSE/RAG 长稳仍需另跑后端全链路测试

## 判定

### 通过的验收项

- 30 分钟持续调用无失败
- 无连接错误、无超时、无空回答
- Ollama 进程未崩溃
- 生成 token 与响应均正常

### 不通过的验收项

- 在线交互延迟：p95 11.1s、p99 17.4s，远超平台目标
- 持续负载下延迟漂移明显
- 27B 模型 RSS 高，且存在持续增长/回收波动

## 与在线模型的关系

此前 RAG + 农业提示词的实测：

- `qwen3.8:27b`：约 **57.66 秒/次**
- `qwen2.5:7b-chat`：约 **18 秒/次**

因此 `qwen3.8:27b` 继续定位为“交叉验证专用 / 离线高质量模式”，不作为在线主模型。
生产在线模型仍需使用独立推理服务、云端模型或专用 GPU 主机，并单独完成 30 分钟 SLO 长稳。

## 下一步建议

1. 使用生产实际模型跑平台级 k6 长稳（SSE、会话、RAG、审核、数据库、内存/GC）。
2. 若坚持用 `qwen3.8:27b` 做平台长稳，建议：
   - 1 VU 固定并发；
   - 短提示词、限制输出 token；
   - 不做大知识库 RAG；
   - 记录延迟漂移而不是套用在线 SLO 阈值；
   - 测试后清理测试 Agent 与配额。
3. 对 Ollama 内存增长做专项观测，确认是否存在模型 runner 泄漏或仅是缓存/显存映射波动。
4. 生产验收仍需独立于本机模型环境。
