### MySQL MGR 故障结论

- MGR 三节点正常时数据一致。
- primary 删除后，MGR 能自动选主。
- ProxySQL 能把写流量切到新 primary。
- 应用在 primary failover 后仍可登录。
- 限制：Pod 重建后当前版本需要手动执行 `START GROUP_REPLICATION`；自动 rejoin sidecar 已移除，因为它会和 Group Replication 启动状态竞争。

### Redis Sentinel 故障结论

- 3 个 Sentinel 能达到投票 quorum。
- 主动 failover 成功后，应用 Sentinel 配置能发现新 master。
- 应用登录在 failover 后仍然正常。
- 限制：Redis 是缓存层，HA 测试期间没有复制旧 RDB 的缓存数据。

## 三、演练后发现的问题

1. **Agent Gateway 资源曾丢失**
   - 节点 drain 时发现 Deployment/Service/Secret 不在集群里。
   - 已从备份清单恢复，当前 `agent-gateway 1/1`，外部 `19001` 返回 200。
   - 后续部署应把 Agent Gateway 纳入正式 Helm/清单管理，避免再次丢失。

2. **MGR 自动 rejoin 未完成**
   - 当前 MGR 缩容到 0，单实例 MySQL 运行中。
   - 若重新启用 HA，Pod 重建后需要执行：

   ```sql
   START GROUP_REPLICATION;
   ```

   - 后续应做独立 rejoin 控制器或使用 MGR Operator。

3. **K8s 控制面不是 HA**
   - 当前 k3d 只有 1 个 server。
   - server 节点故障时 K8s API 不可用。

4. **数据集仍是单点**
   - MySQL/Redis 当前已恢复单实例。
   - PostgreSQL/pgvector、MinIO、ES、Qdrant 仍是单实例。
   - 按既定范围，MinIO 分布式和 Longhorn/Ceph 暂不实施。

发现的问题：

- CoreDNS、local-path-provisioner、metrics-server 重启后被调度到 agent 节点

- 将 CoreDNS、local-path-provisioner、metrics-server、busybox 镜像直接导入 3 个 K3s 节点
- 重启系统 Pod 和应用 Deployment
- 平台 health、登录、Agent Gateway 全部恢复 200

二次复测：

### 8.5 已知限制

- 备份和监控都在 UTM 单机，非高可用；宿主机故障会同时影响监控与备份。
- 备份尚未异地化，不能抵御宿主机磁盘/整机故障。
- cAdvisor 通过 kubelet 采集，依赖 kubelet token（默认一年）和 k3d 当前节点 IP。
- 监控栈端口当前在 UTM 内网监听；生产应加防火墙或反向代理/TLS。
- 本次部署期间曾出现 k3d serverlb 异常退出（Exit 137），K8s 节点重启后 NodePort 短暂不可用；已执行 k3d cluster stop/start 恢复，当前应用入口 200，Prometheus 目标全部 up。后续应给 k3d/Docker 增加异常自愈和开机顺序验证。
