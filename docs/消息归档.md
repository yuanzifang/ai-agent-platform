# 消息归档与保留

对应架构设计 8.4：`message` 默认保留 90 天，过期归档；V49 增加 `message_archive`。

## 1. 行为

`MessageArchiveService` 每天 03:40（可配）执行：

1. 读取 `message` 的月分区，只选择**整个分区都早于保留截止日**的分区。
2. 把该分区全部消息写入 `message_archive`（保留原字段 + `archived_at`）。
3. 按主键 join 校验该分区每一行都已归档。
4. 校验通过才执行 `ALTER TABLE message DROP PARTITION`。
5. 重复执行幂等：已归档/已删除分区的消息不会重复；`pmax` 永不自动删除。

保留窗口是 **90~120 天**：月中不会为了“刚好 90 天”拆分区，整月到期后才删除，避免误删当月新消息。

示例（保留 90 天，当前 2026-10-20，截止 2026-07-22）：

- `p202606`（< 2026-07-01）整月都早于截止日 → 可归档并删除；
- `p202607`（< 2026-08-01）包含 7 月数据，不满足整月过期 → 保留。

## 2. 配置

```yaml
message:
  archive:
    enabled: ${MESSAGE_ARCHIVE_ENABLED:true}
    retention-days: ${MESSAGE_RETENTION_DAYS:90}
    cron: ${MESSAGE_ARCHIVE_CRON:0 40 3 * * *}
```

- 应用账号需要 `SELECT / INSERT / DELETE / ALTER`（`DROP PARTITION`）。
- 归档表不分区，长期保留；目前没有归档表自身的清理策略。
- 运行失败不会删除分区；日志会记录 `partition/source/archive` 数量。

## 3. 手动触发

平台管理员接口（需登录 + `X-Tenant-Id` 选择租户；会写审计 `message.archive`）：

```bash
curl -X POST http://127.0.0.1:8080/api/v1/platform/maintenance/message-archive \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "X-Tenant-Id: 1"
```

返回示例：

```json
{
  "enabled": true,
  "retentionDays": 90,
  "cutoff": "2026-07-22",
  "archivedRows": 3,
  "droppedPartitions": 6,
  "partitions": ["p202601", "p202602", "p202603", "p202604", "p202605", "p202606"],
  "skipped": false
}
```

说明：

- 前 5 个月可能是空分区，也会被顺手删除；`archivedRows` 只统计实际归档行数。
- 同一时刻只允许一个归档任务；重复调用会返回 `skipped=true` 或 0 条。
- 非平台管理员返回 403。
- 手动触发/定时任务共用同一段安全校验逻辑。

## 4. 查询归档

归档消息不再出现在正常会话/消息列表：

```sql
SELECT id, conversation_id, role, content, created_at, archived_at
FROM message_archive
WHERE conversation_id = ?
ORDER BY created_at DESC
LIMIT 50;
```

如需恢复某条消息到活跃表，必须插入 `message` 并确保 `created_at` 对应分区存在（否则进 `pmax`）；当前没有“一键恢复”接口，避免误操作。

## 5. 备份与恢复

`message_archive` 是普通 InnoDB 表，已包含在 MySQL 全量备份/恢复演练中；备份脚本自动统计 80 张表（V50 后）。恢复后归档表可独立查询。

## 6. 已验证

2026-10-20 本机：

- 副本库插入 3 条 2026-06 的旧消息 → 手动归档：
  - `archivedRows=3`，`message_archive` 3 行；
  - `p202606` 被删除，当前消息数仍为 96；
  - 再次调用 `archivedRows=0`、`droppedPartitions=0`；
  - 审计记录 `message.archive`。
- 非平台管理员调用返回 403。
- 真实库 V49：Flyway 16ms 完成，`message_archive` 创建成功，分区数不变。
- 归档后完整 E2E：**28/28**；单测 **48/48**。
- 归档后备份 + 恢复演练：MySQL **80 张表**校验和不一致 0（审计 226），PgVector 2 表一致。

## 7. 边界

- 归档表当前无限增长；后续需要冷存储/导出和归档保留期。
- 历史消息归档后，正常对话回看不再显示；已预留 SQL 查询，未做前端“归档消息”入口。
- 会话本身（`conversation`）的软删保留期未自动清理。
- 早于 2026-01 或已进入 `pmax` 的消息不会自动归档。
- 大分区 `INSERT SELECT`/`DROP PARTITION` 会占用 I/O；生产建议低峰执行并观察锁等待。
- Compose/Helm 下未实跑。
