# 向量检索性能基准（2026-10-26）

## 环境

- PostgreSQL 16.15
- pgvector 0.8.7（`pgvector/pgvector:pg16`）
- 表：`tenant_1.embeddings_1024`
- 向量维度：1024
- 数据：随机向量，仅用于测延迟，不代表语义质量
- 索引：

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_embeddings_1024_hnsw
ON tenant_1.embeddings_1024
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

## 结果

查询与当前代码一致：

```sql
SET hnsw.iterative_scan = relaxed_order;
SET hnsw.ef_search = 100;

SELECT id
FROM tenant_1.embeddings_1024
WHERE metadata->>'knowledge_base_id' = '1'
  AND 1 - (embedding <=> :query) >= 0.5
ORDER BY embedding <=> :query
LIMIT 5;
```

| 数据量 | 计划 | 延迟 |
| ---: | --- | ---: |
| 10,000 | Seq Scan + Sort（规划器认为小表顺序扫描更便宜） | 87.7ms |
| 100,000 | HNSW Index Scan（带 metadata 过滤 + 阈值过滤） | **0.59ms** |

100k 行时执行计划确认使用：

```text
Index Scan using idx_embeddings_1024_hnsw on embeddings_1024
  Order By: (embedding <=> $0)
  Filter: (metadata->>'knowledge_base_id' = '1' AND ...)
```

- `CREATE INDEX CONCURRENTLY ... USING hnsw` 语法验证通过；
- `SET hnsw.iterative_scan = relaxed_order` 在 0.8.7 可用；
- 过滤查询仍能走 HNSW，满足需求文档“知识库检索 < 500ms”的目标（本机、随机向量）。

### 100k 并发压测

同样 100k×1024 维数据，`pgbench` 8 客户端 / 4 线程，持续 20 秒，
查询包含知识库过滤 + 阈值过滤 + `ORDER BY embedding <=> query LIMIT 5`：

```text
number of clients: 8
number of transactions actually processed: 102856
number of failed transactions: 0
latency average = 1.556 ms
tps = 5142.6
```

8 并发下平均延迟 1.56ms、约 5.1k TPS，未出现失败事务。

## 说明

- 10k 行时规划器选择顺序扫描，延迟仍低于 500ms；不必强制 HNSW。
- 真实语义查询的召回质量与 embedding 模型相关，见 `docs/中文Embedding评测.md`。
- 这是单机、单查询基准，不是并发压测；上线前需补：
  - 10–50 并发下的 P95/P99；
  - 100 万行时的索引构建时间与内存；
  - 多知识库过滤下的召回率/延迟；
  - MySQL 分段批量写入的大文档耗时。
- 若后续知识库数量很多，HNSW 全局索引 + metadata 过滤在极端过滤比下可能退化，
  再评估按租户/知识库分区或 partial HNSW index。

## 100k / 250k 无过滤 P95/P99（2026-10-26）

### 环境与方法

- 临时 `pgvector/pgvector:pg16` 容器，`--shm-size=1g`；
- 1024 维随机向量；
- HNSW：`m=16, ef_construction=64`；
- 查询只做 `ORDER BY embedding <=> query LIMIT 5`，不附加知识库/阈值过滤；
- `pgbench` 8/16/32 客户端/线程，10 秒，日志逐事务统计 P50/P95/P99；
- 脚本：`ROWS=250000 CLIENTS="8 16 32" DURATION=10 scripts/vector-p99-benchmark.sh`

## MySQL 批量写入优化

MySQL JDBC URL 已开启：

```text
rewriteBatchedStatements=true
cachePrepStmts=true
prepStmtCacheSize=250
```

知识库父子块批量写入每批 500 行，开启后驱动会把多行 INSERT 合并发送，避免 batch 退化为逐条 SQL。
真实大文档写入耗时仍需在独立 MySQL 环境补测。

## 100 万行 × 1024 维 HNSW（2026-10-27）

### 环境

- 宿主：macOS，128GB 内存，16 CPU；
- 本地 PostgreSQL 17.11 + pgvector 0.8.7；
- 1024 维随机向量，100 万行；
- HNSW：`m=16, ef_construction=64`；

- 生产过滤比、冷缓存和多知识库场景仍需独立环境验证。

## MySQL JDBC 批量写入实测（2026-10-27）

临时 MySQL 8.4 容器，表 `chunk_bench`，每批 500 行，50000 行文本分段：

| JDBC 配置 | 耗时 | 吞吐 |
| --- | ---: | ---: |
| `rewriteBatchedStatements=false` | 9.293s | 约 5,380 行/s |
| `rewriteBatchedStatements=true` | 0.458s | 约 109,170 行/s |

结论：开启 `rewriteBatchedStatements=true` 后约 20 倍提升，当前知识库分段/父块批量写入已启用该配置。

说明：这是 JDBC 批量 INSERT 微基准，不含解析、嵌入和 PgVector 写入；真实大文档端到端耗时仍需按文档类型复测。
