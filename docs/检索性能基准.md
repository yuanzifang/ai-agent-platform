# 向量检索性能基准（2026-10-26）

## 环境

- PostgreSQL 16.15
- pgvector 0.8.7（`pgvector/pgvector:pg16`）
- 表：`tenant_1.embeddings_1024`
- 向量维度：1024
- 数据：随机向量，仅用于测延迟，不代表语义质量
- 索引：

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_embeddings_1024_hnsw
ON tenant_1.embeddings_1024
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

## 结果

查询与当前代码一致：

```sql
SET hnsw.iterative_scan = relaxed_order;
SET hnsw.ef_search = 100;

SELECT id
FROM tenant_1.embeddings_1024
WHERE metadata->>'knowledge_base_id' = '1'
  AND 1 - (embedding <=> :query) >= 0.5
ORDER BY embedding <=> :query
LIMIT 5;
```

| 数据量 | 计划 | 延迟 |
| ---: | --- | ---: |
| 10,000 | Seq Scan + Sort（规划器认为小表顺序扫描更便宜） | 87.7ms |
| 100,000 | HNSW Index Scan（带 metadata 过滤 + 阈值过滤） | **0.59ms** |

100k 行时执行计划确认使用：

```text
Index Scan using idx_embeddings_1024_hnsw on embeddings_1024
  Order By: (embedding <=> $0)
  Filter: (metadata->>'knowledge_base_id' = '1' AND ...)
```

- `CREATE INDEX CONCURRENTLY ... USING hnsw` 语法验证通过；
- `SET hnsw.iterative_scan = relaxed_order` 在 0.8.7 可用；
- 过滤查询仍能走 HNSW，满足需求文档“知识库检索 < 500ms”的目标（本机、随机向量）。

## 说明

- 10k 行时规划器选择顺序扫描，延迟仍低于 500ms；不必强制 HNSW。
- 真实语义查询的召回质量与 embedding 模型相关，见 `docs/中文Embedding评测.md`。
- 这是单机、单查询基准，不是并发压测；上线前需补：
  - 10–50 并发下的 P95/P99；
  - 100 万行时的索引构建时间与内存；
  - 多知识库过滤下的召回率/延迟；
  - MySQL 分段批量写入的大文档耗时。
- 知识库数量很多时，全局 HNSW + metadata 过滤在极端过滤比下可能退化；
  当前已提供按知识库 partial HNSW（见后文），仍需结合索引数量、磁盘和写入放大约束调参。

### 低选择比自适应策略（应用已实现）

向量检索在满足以下条件时自动改用物化过滤集 + 精确排序：

- 表总行数 ≥ `pgvector.filtered-exact.min-rows`（默认 200000）；
- 当前知识库命中行数 ≤ `pgvector.filtered-exact.max-rows`（默认 50000）；
- 当前知识库命中占比 < `pgvector.filtered-exact.threshold`（默认 0.25）。

配置：

```yaml
pgvector:
  filtered-exact:
    threshold: 0.25
    min-rows: 200000
    max-rows: 50000
```

`max-rows` 是 2026-10-27 应用层压测后新增的约束：1M 表/20%（20 万行）时，
物化过滤集 + 排序的 8 并发 P50 约 **2.76s**，而同一查询走全局 HNSW P50 约 **109ms**。
因此精确回退只保留给小知识库；大知识库即使过滤比低也走 HNSW/partial HNSW。
低于 `max-rows` 的 1%/10% 小知识库仍可走物化过滤，避免全局 iterative scan 放大。

### 按知识库 partial HNSW（应用已实现）

应用会周期性为达到阈值的知识库创建专用 partial HNSW：

```sql
CREATE INDEX idx_embeddings_1024_hnsw_kb_4
ON tenant_1.embeddings_1024 USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64)
WHERE metadata->>'knowledge_base_id' = '4';
```

配置：

```yaml
pgvector:
  hnsw:
    partial:
      enabled: true
      min-rows: 50000
      max-indexes: 20
      max-ratio: 0.4
      prune: false
      reconcile-interval-ms: 86400000
      initial-delay-ms: 300000
```

维护策略：

- 按知识库行数从大到小，每张维度表最多维护 `max-indexes` 个 partial 索引；
- 达到 `min-rows` 的知识库才建索引，避免小知识库造成索引数量和写入放大失控；
- 命中占比超过 `max-ratio`（默认 0.4）的知识库不建 partial；矩阵测试中 50% 命中时规划器选择全局 HNSW，partial 索引未被使用；
- 默认保留历史索引（`prune=false`）；确认存储/写放大预算后可开启清理；
- 多副本通过 Redis 锁 `lock:vector:partial:reconcile` 互斥，锁 TTL 1 小时；未拿到锁的实例跳过；
  本机双后端 18081/18082 同时启动实测，18082 日志为 `维护跳过：已有实例在执行`，且维护结束后锁已释放；
- 下一轮维护会删除 `CREATE INDEX CONCURRENTLY` 中断留下的 invalid index 并重建；
- 查询条件使用知识库 ID 字面量，PostgreSQL 才能把
  `WHERE metadata->>'knowledge_base_id' = '<id>'` 匹配到对应 partial 索引；
- 有 partial 索引时跳过低选择比物化精确排序；没有索引的知识库继续走全局 HNSW /
  `filtered-exact` 回退。

1M×1024 随机向量、10 个知识库各 100k 行实测：

| 查询 | 索引 | 单次耗时 |
| --- | --- | ---: |
| kb=4，10% 过滤，有阈值 0.5 | 全局 HNSW | 0.91ms |
| kb=4，10% 过滤，有阈值 0.5 | partial HNSW | 0.35ms |
| kb=5，10% 过滤，无阈值 | 全局 HNSW | 0.55ms |
| kb=4，10% 过滤，无阈值 | partial HNSW | 0.35ms |

并发平均延迟（10 秒 pgbench）：

| 客户端 | 全局 HNSW | partial HNSW |
| ---: | ---: | ---: |
| 8 | 0.277ms | 0.230ms |
| 32 | 0.751ms | 0.618ms |

索引体积：100k 行 partial HNSW 约 **777MB**，1M 全局 HNSW 约 **7.8GB**。
`EXPLAIN` 已确认查询从 `vectors_hnsw` 切换到 `idx_vectors_hnsw_kb_4`。
