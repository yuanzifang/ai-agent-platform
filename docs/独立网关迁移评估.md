# 独立网关迁移评估（决策记录）

日期：2026-11-02

## 决策

**暂不引入独立网关，不做迁移。**

继续使用：

```text
Ingress / nginx
  → Spring 业务网关（当前自定义模块）
  → 业务服务 / Agent runtime gateway
```

Spring Cloud Gateway 只记录为后续可选项，不进入当前 MVP 范围。

## 当前网关分层

| 层 | 职责 | 是否迁移 |
| --- | --- | --- |
| Ingress / nginx | TLS、域名、静态资源、基础反代 | 不迁移 |
| Spring 业务网关 | 路由、API Key、限流、WAF、重试、熔断、日志、SSE/WS | 未来可迁 |
| Agent runtime gateway | Agent 部署令牌、调用方 Key、配额、用量、对话链路 | **不迁移** |
| Agent nginx | 每 Agent 的 `/v1` 透明反代 | 不迁移 |

## 为什么暂不迁移

1. 当前能力已经覆盖 MVP：
   - 动态路由
   - API Key
   - Redis 限流/配额
   - WAF/请求校验
   - 超时/重试/熔断
   - SSE/WebSocket
   - 请求日志

2. 再引入独立网关会增加：
   - 一个新进程/部署/监控/升级面
   - 一套重复的鉴权、路由、限流逻辑
   - 双跑和数据一致性成本

3. 当前瓶颈不在网关吞吐，优先事项是业务验证、Agent 发布、测试与模型稳定性。

## 如果未来迁移，哪些容易/困难

| 能力 | 迁移难度 |
| --- | --- |
| 路由管理 API / 表结构 | 低 |
| API Key 鉴权 Filter | 中 |
| Redis 限流/日配额 | 中 |
| 请求日志 | 低 |
| WAF / 签名 / Schema 校验 | 中 |
| 多上游权重、重试、熔断 | 中高 |
| SSE 透传 | 中高（Servlet `StreamingResponseBody` → WebFlux） |
| WebSocket 代理 | 高 |
| Agent runtime gateway | 不建议迁移 |
| 管理 UI | 低（接口不变） |

代码形态差异：

```text
当前：Spring MVC + HttpClient + StreamingResponseBody + Servlet WebSocket
SCG：WebFlux + WebFilter/GatewayFilter + WebClient + Flux<DataBuffer>
```

因此不是复制类，而是重写代理层并做双跑验证。

## 迁移触发条件

只有出现以下情况才重新评估：

- 外部 API QPS 显著增长，需要网关独立扩缩容
- 网关需要独立发布/回滚/故障隔离
- 多团队、多服务统一接入，需要标准 Filter/插件体系
- 需要复杂流量治理：灰度、镜像、请求改写、统一认证
- 当前 Servlet/线程模型成为真实瓶颈

## 未来迁移原则（仅记录）

```text
Ingress / nginx
  → Spring Cloud Gateway（独立）
     - 通用路由/API Key/限流/WAF/日志/SSE/WS
  → backend
     - Agent runtime gateway
     - Chat / RAG / Workflow / 业务逻辑
```

- Agent runtime gateway 保留在后端，SCG 只转发。
- 管理 API 和数据库路由表尽量保持不变。
- 先低风险路由双跑，再迁 SSE/WS，最后下线旧代理。
