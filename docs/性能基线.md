## 100 VU 分层 profiling（2026-10-27，mock）

为判断 100 VU 延迟来源，在相同 100 VUs / 每轮间隔 2s / 2 分钟条件下分层：

| 层级 | 完成/请求 | chat_ok | TTFB avg / p95 | 结论 |
|---|---:|---:|---:|---|
| 直连 mock `/v1/chat/completions` | 5,827 | — | 0.96ms / 2.06ms | mock 上游不是主要瓶颈 |
| 后端无 RAG/审核 | — | 100% | 1,412.44ms / 1,564.85ms | 平台 SSE/DB 基线已略超 1.5s |
| 后端 RAG + 审核 | 2,919 | 100% | 2,137.69ms / 2,693.71ms | RAG/审核再增加约 1–3s |

连接池 30/20 与 10/8 复测均未改善（p95 4,901.91ms / 3,151.24ms）。结论：**mock 上游不是主因，瓶颈在平台侧 SSE/DB/线程调度，RAG 检索进一步放大排队**；需要继续做请求分段计时和连接池/线程池 profiling。

新增 `RequestTimingFilter`（默认关闭）：设置 `REQUEST_TIMING_ENABLED=true` 后，首字节超过 `REQUEST_TIMING_SLOW_MS`（默认 1000ms）会记录 method/URI/firstByteMs，用于定位 SSE 请求进入业务代码前的排队。

### 查询 embedding 缓存复测（2026-10-27）

`EmbeddingService.embedQuery` 增加进程内查询缓存（默认 TTL 300s、最多 2000 条），避免重复 FAQ/检索问句反复调用 embedding 上游。100 VU 前先预热一次同一问句，再执行 2 分钟压测：

| 指标 | 无缓存（此前） | 查询缓存（预热后） |
|---|---:|---:|
| chat_ok / HTTP 失败 | 100% / 0 | 100% / 0 |
| 首 Token p95 | 2,693.71ms | **1,972.55ms** |
| RAG 检索 span avg | 1,221.1ms | **51.3ms** |
| embedding 子步骤 | 约 1,788–1,962ms | **约 5–6ms** |

说明：缓存显著降低了重复问句的检索耗时，但 100 VU 首 Token p95 仍超过 1.5s。已补进程内 single-flight：同一模型/问句的并发冷查询只打一次 embedding 上游，单测覆盖。100 VU 无预热复测：chat_ok 100%、HTTP 失败 0，但 TTFB p95 **4,950.59ms**；检索子步骤已降到 embedMs 4–8ms，说明剩余延迟主要在平台请求排队/SSE 调度，而不是 embedding 上游。另增加可选 Redis query embedding 缓存（有 Redis 时跨实例共享，异常回退本地）；跨实例容器级 single-flight 仍未做。结果仍为 mock 模型。
