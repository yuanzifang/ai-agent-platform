# 大表分区与维护

对应架构设计 8.4。V48 将高增长表按 `created_at` 月分区，并增加自动补齐未来分区的维护任务。

## 1. 范围

| 表 | 分区 | 主键/唯一键调整 |
|---|---|---|
| `agent_trace` | 月 | PK `(id, created_at)`；`uk_trace(trace_id)` 降为普通索引 `idx_trace_id` |
| `agent_span` | 月 | PK `(id, created_at)` |
| `audit_operation` | 月 | 原 PK 已是 `(id, created_at)`，仅把年度分区改为月分区 |
| `conversation` | 月 | PK `(id, created_at)`；`uk_session(session_id)` 改为 `uk_session_created(session_id, created_at)` |
| `message` | 月 | PK `(id, created_at)` |
| `system_log` | 月 | PK `(id, created_at)` |

V48 初始创建 **2026-01 .. 2028-12** 共 36 个月分区 + `pmax`，历史数据按 `created_at` 自动落入对应月份；不在范围内的数据进入 `pmax`。

## 2. 为什么必须改主键/唯一键

MySQL 分区表要求所有唯一键（含主键）包含分区列。因此：

- `agent_trace.trace_id` 不再由数据库唯一约束保证；Trace ID 由应用生成（UUID/雪花），`idx_trace_id` 仍支持详情查询。详情查询已加 `LIMIT 1` 兜底。
- `conversation.session_id` 的唯一约束变为 `(session_id, created_at)`。应用创建会话前会先查重；同一 session_id 并发首次创建仍由业务层保证。若需要数据库级 session 唯一，只能放弃按时间分区或增加独立映射表。
- `message`/`agent_span`/`system_log` 的 `id` 仍为 `AUTO_INCREMENT`，且是复合主键第一列，MyBatis-Plus 的 `insert`/`selectById`/`updateById` 正常。
- 这些表没有外键（MySQL 分区表不支持外键）；后续新增外键需要重新评估。

## 3. 自动补齐未来分区

`PartitionMaintenanceService`：

- 启动时执行一次；之后按 cron 执行（默认每天 02:20）。
- 读取 `information_schema.partitions`，找到最后一个非 `pmax` 边界。
- 用 `ALTER TABLE ... REORGANIZE PARTITION pmax INTO (...)` 补齐到“当前月 + months-ahead”。
- 只补未来，**不会自动删除历史分区**。

配置：

```yaml
storage:
  partition:
    enabled: ${PARTITION_MAINTENANCE_ENABLED:true}
    months-ahead: ${PARTITION_MONTHS_AHEAD:3}
    cron: ${PARTITION_MAINTENANCE_CRON:0 20 2 * * *}
```

生产要求：

- 应用数据库账号需要 `ALTER`（至少对上述 6 张表）权限；否则启动日志会出现“分区维护失败”，但不影响业务读写（新数据进入 `pmax`）。
- 每次 `REORGANIZE pmax` 只操作空/少量 `pmax`，正常很快；仍建议低峰执行，并避免长事务。
- 若 `pmax` 已积累大量历史数据，`REORGANIZE` 会搬数据，应在维护窗口前先人工拆分/归档。

## 5. 查询与分区裁剪

分区裁剪依赖 `created_at` 条件：

```sql
-- 会裁剪到单月分区
SELECT * FROM message
WHERE created_at >= '2026-10-01' AND created_at < '2026-11-01'
ORDER BY id DESC LIMIT 20;
```

只按 `conversation_id`/`id` 查询时，MySQL 可能扫描所有分区：

```sql
SELECT * FROM message WHERE conversation_id = ? ORDER BY created_at DESC LIMIT 20;
```

高增长场景建议列表/导出接口都带时间范围；现有消息按会话查询仍可用，但数据量上来后应补 `created_at` 范围。`EXPLAIN` 可确认实际访问分区。

## 6. 保留与归档现状

- `system_log`：LogCaptureService 仍按 `system.log.retention-days=7` 执行行级 DELETE；分区让清理/查询更可控，但尚未切换为“导出后 DROP PARTITION”。
- `message`：已实现 90 天归档（V49 `message_archive` + 整月分区校验后 DROP）；详见 [`消息归档.md`](消息归档.md)。
- `agent_trace`/`agent_span`：当前不自动清理，避免影响评测/排障；后续按配置做归档。
- `audit_operation`：按合规保留，禁止自动 DROP；归档与保留期需单独审批。
- `pmax` 中的超范围数据不会自动迁移，需维护窗口人工处理。
