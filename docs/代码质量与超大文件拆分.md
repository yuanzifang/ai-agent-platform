# 代码审查与超大文件拆分记录（v0.3.2 发布前）

日期：2026-11-02

## 1. 审查范围与结论

本轮针对 `v0.3.1` 之后合入主干的改动做发布前审查，重点检查：

- 知识库解析/检索/权限链路；
- 知识图谱社区摘要与 GraphRAG 召回；
- 超大 Java 类；
- 前端构建与既有单测。

结论：发现并修复了 4 个高置信度问题；两个超过 2000 行的生产 Java 服务已拆分到 2000 行以内；后端全量测试通过。

## 3. 发现并修复的问题

### 3.1 社区摘要自动刷新实际会失败且不落库

位置：`KnowledgeGraphService.autoRefreshCommunities`

原实现：

- 构造 `Viewer(null, List.of())` 调用 `summarizeCommunities`；
- `canView` 对 `userId == null` 直接返回 false，异步任务必然 403；
- 即使有权限，调用的是只生成内存摘要的 `summarize`，没有调用持久化的 `rebuild`，社区索引不会更新；
- 日志仍会记录“完成”，容易误判。

修复：

- 使用知识库创建者作为内部 viewer（`createdBy` + `OWNER`），满足 PRIVATE/PARTIAL/TENANT 的创建者可见规则；
- 改为调用 `KnowledgeGraphCommunityService.rebuild`，真正写入社区表并更新社区向量索引；
- 自动刷新上限固定为 10 个社区，避免一次提交触发过多模型调用；
- 保留 `knowledge.graph.auto-refresh-communities` 开关。

### 3.2 社区重建接口权限过宽

位置：`KnowledgeGraphService.rebuildCommunities`

原实现使用 `requireView`，但该接口会写入/覆盖社区摘要和向量，属于编辑操作。已改为 `requireEdit`，与 `embedEntities` 等同类写接口一致。

### 3.3 文档重试未清理旧图谱数据

位置：`KnowledgeService.retryDocument`

重试前清理了分段、父块、向量和图片，但没有清理该文档贡献的自动图谱；重新解析后可能残留旧实体/关系并产生重复证据。已补 `graphService.deleteByDocument`，与 `cleanupPartial` 的清理范围保持一致。


### 3.4 模型失败时用社区名称覆盖已有摘要

位置：`KnowledgeGraphCommunityService.summarize/rebuild`

原实现生成摘要失败时把 `community.name` 当摘要写回；如果只是模型短时不可用，自动刷新会用名称覆盖已有有效摘要。现在失败行会标记 `summaryFailed`，`rebuild` 跳过该社区并保留旧摘要；同时自动刷新优先使用平台默认模型，只有未配置时才回退到 `deepseek-flash`。

### 3.5 合并 main 后新增测试的夹具问题

合并发布分支与 main 时发现 3 个新增测试在完整 `mvn test` 下失败，均为测试夹具/断言问题，不是生产逻辑回归：

- `MetricsServiceTest`：自定义区间断言把当前区间结束时间写成了开始时间，已改为 `currentEnd`；
- `ObservabilityServiceTraceTest`：使用 MyBatis-Plus Lambda Wrapper 前未初始化 `AgentTrace` 的 TableInfo，已在测试内初始化；
- `UserAdminServiceInviteTest`：直接 `new UserAdminService` 时未注入 `@Value frontendBase`，已用测试反射补默认值；
- `AuthServiceLoginTest`、`ConversationServiceAttachmentTest`、`UserAdminServiceInviteTest` 的 `insert(any())` 在 MyBatis-Plus 3.5.7 下与集合重载歧义，已改为带具体实体类型的 `any(X.class)`。


### 3.6 本轮额外加固

发布前审查还修复了以下高置信度问题：

- **嵌入缓存键不一致**：缓存按 `contentHash` 写入，却用原始文本查缓存，导致缓存永远 miss；已统一按 hash 查找和回填。
- **人工复核状态残留**：`RESOLVED` 后历史 `parseWarning` 仍包含“人工复核”，列表继续显示待复核；现在仅 `PENDING`（或历史 null）才算待复核。
- **覆盖上传继承旧解析配置**：`updateById` 跳过 null，覆盖上传不带解析配置时会保留旧 OCR/视觉配置或 PDF 密码；已显式清空。
- **知识库分段 ACL 非原子**：抽取为 `KnowledgeChunkAclService`，先更新向量 metadata 再写 MySQL；MySQL 失败时补偿旧向量 ACL，并保留事务回滚。
- **`maxTopK` 静默截断**：混合检索下游硬编码上限 20，已与知识库允许的 50 对齐。
- **网关 API Key 跨路由枚举**：`apiKeys/createKey` 先校验路由归属，阻止通过任意 routeId 读取/创建 Key。
- **网关请求/上游响应内存上限**：请求按 Content-Length 和 `readNBytes(MAX+1)` 限制；上游响应改为流式读取并在 10MB 上限处中止。
- **API 工具重试副作用**：只对 GET/HEAD/OPTIONS 或显式 Idempotency-Key 的请求重试；4xx 不重试，非幂等写请求的网络异常不自动重试。
- **聊天备用模型许可泄漏**：主/备用模型共用一次并发许可，并在 finally 释放。
- **Checkpoint 租户上下文**：显式租户的 `save/get` 在异步/Reactor 线程内恢复 TenantContext，避免断线续传读不到 checkpoint。
- **并行工作流审批角色**：并行门禁取分支内审批节点的最高角色要求，避免用 PARALLEL 节点空角色绕过 ADMIN 审批。
- **工作流恢复并发**：恢复使用 `UPDATE ... WHERE status='FAILED'` 条件抢占，防止两个实例同时恢复同一运行。
- **社区摘要 ACL/失效**：保存/搜索社区摘要时要求成员实体全部对当前 viewer 可见；文档/知识库删除或重解析会失效对应社区及图向量。
- **删除顺序**：对象存储/图片/向量清理改为 MySQL 事务提交后执行，避免数据库回滚后文件已丢。
- **部署失败状态**：移除部署方法的数据库事务包裹，Docker/K8s 外部操作失败后 `FAILED` 状态、事件和错误信息可独立落库。
- **工作流嵌套副作用**：恢复检查递归识别 LOOP/PARALLEL 内的 TOOL/HANDOFF/AGENT 节点。

PR #38 已补充 `KnowledgeUploadPolicy`、并行审批门禁、聊天附件注入和图片识别等回归测试；当前后端口径为 630 个用例。

其中“并行工作流恢复的嵌套副作用”“删除外部存储/向量先于数据库事务提交”等结构性风险仍保留，列入第 5 节。

## 5. 发布前剩余风险

- `KnowledgeGraphService.autoRefreshCommunities` 默认开启，会在图谱提交后异步调用模型生成社区摘要；如模型额度敏感，应通过 `sys_config` 关闭。
- 社区摘要、实体向量的检索仍依赖 pgvector 索引可用性；索引不可用时回退 MySQL 余弦计算（有 500 条上限），规模增长后需要监控延迟。
- 分段 ACL 的 MySQL 与向量库更新仍不是强一致；已加事务边界，但跨存储最终一致性仍未实现。
